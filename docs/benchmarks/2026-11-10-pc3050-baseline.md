# PC 3050: a second bench machine, Sync 11 baseline (2026-11-10)

PC 3050 shows how our changes behave on an ordinary PC. Its fps are never compared with the main PC's: only before/after
on this same machine counts.

## The machine
- DESKTOP-5R4IKRB, Windows (French locale), user `yanis`, reached over SSH from the main PC (key login, cmd.exe shell).
- Intel Core i5-10400F (6 cores / 12 threads, AVX2, no integrated GPU), 32 GB RAM, NVMe SSD (CT500P3SSD8).
- NVIDIA GeForce RTX 3050 8 GB, driver 591.86.
- **PCIe link: Gen 3 x4 under load** (`nvidia-smi`: link max 16x, current 4x; the host is Gen 3), and BAR1 is 256 MiB
  (no Resizable BAR). So host <-> GPU copies get ~3-4 GB/s, against Gen 4/5 x16 with ReBAR on the main PC.
- On Wi-Fi (the 34 GB game copy took ~25 min).

## How to run benches there
From the main PC (nothing runs on the main PC itself):

```
ssh -o BatchMode=yes yanis@192.168.31.219 "C:\OOT\tools\python\python.exe -I C:\OOT\scripts\pcbench.py <label> <scene> [ENV=VALUE ...]"
ssh -o BatchMode=yes yanis@192.168.31.219 "C:\OOT\tools\python\python.exe -I C:\OOT\scripts\pcsum.py <label> ..."
```

`pcbench.py` runs `tools/bench/run_bench.py --exe C:\OOT\game\HeyListen.exe --scene <scene> --duration 110 --warmup-s 66
--fps-limit 360` with the extra env, and beside it samples once a second `nvidia-smi` (VRAM used, GPU utilisation,
clock, power, PCIe gen/width) and the whole machine's CPU (`GetSystemTimes`) into `<label>\smi.csv`. It refuses to start
when a game runs or the save differs from `C:\OOT\user-save-backup`; afterwards it checks `tasklist` and compares the save
with the backup byte for byte. `pcsum.py` prints fps / 1% low / p99 and the samples after the 66 s cut.
For a series, a .bat calling `pcbench.py` per run (`baseline.bat`: 3 rounds x 3 scenes, interleaved).

run_bench.py needed no change: it takes the game folder from `--exe` (cwd = the exe's folder, saves from
`<exe folder>\user\save`), and `tasklist` CSV parsing works under the French locale. Game runs started over SSH run in
session 0 (no window on the user's desktop; the swapchain is created and presents work). Whether a run on the
interactive desktop gives other numbers was not checked (it would need a scheduled task or similar on that PC).

Changed in the repo: `tools/bench/jobtrace.py` crashed (TypeError) when given `--samples` without `--maps`, which cut the
report before the concurrency and wake-latency sections. It now says the sample split is skipped and goes on.
No Sync 11 map files exist on the main PC, so the samples were not attributed to functions.

## What limits the frame
GPU time (`RX_VK_PASS_TIMING=1`, one run each, inflated by the timestamps; per frame):

| | kokiri-idle | castle-move |
|---|---:|---:|
| in all | 37.2 ms | 33.2 ms |
| recordings (passes 14.7 / 12.2, dispatches 4.7 / 4.5, barriers, write-backs) | 22.5 ms | 19.4 ms |
| upload command buffers | 14.7 ms | 13.8 ms |
| of them `msync scatter` (CPU pages -> VRAM mirrors) | **11.8 ms, 33.6 MB** | **7.8 ms, 22.1 MB** |
| `rbrefresh scatter` | 2.1 ms | 1.8 ms |

The msync scatter moves ~2.8 GB/s: the PCIe Gen 3 x4 link. The same 31-37 MB a frame are synced on the main PC
(TICK-045 logs), where the replay's "memory sync" is 0.4-0.8 ms a frame; here it is 12.7-15.4 ms.

CPU side (`HOS_JOBTRACE` + `HOS_SAMPLE_ALL`/`HOS_SAMPLE_NS`, 4 s at 90 s, `tools/bench/jobtrace.py`):

| main thread, ms a frame | kokiri-idle (38.8 ms frames) | castle-move (44.4 ms) |
|---|---:|---:|
| job group wait (lr 0x80080188) | 13.6 | 14.5 |
| of it: work on the path / wake / vcore waits | 13.1 / 0.41 / 0.01 | 13.9 / 0.45 / 0.05 |
| f_83acfb90's event (lr 0x83acfcf4) | 1.8 | 1.6 |
| SleepThread polls | 2.6 | 2.3 |
| main thread "working" (guest code and the engine's submit) | 20.8 | 25.6 |

Main thread samples (no maps, by module): 34-36% of them have the NVIDIA driver in the stack with ntdll as the leaf, i.e.
the main thread is blocked inside a driver call for ~13 ms a frame; guest code + runtime are only 11-12%.
On the main PC the fence/GPU waits were < 0.2 ms (TICK-037).

**Verdict: GPU-bound, and mostly by the PCIe link.** The GPU is busy ~84% at full clock, a third of its time on
host -> VRAM mirror syncs, and the main thread waits for it in the driver. The job chain is also ~2x the main PC's
(13 vs 7 ms a frame): without the ~13 ms of driver waits the main thread's frame would be ~25-26 ms (~40 fps,
a rough estimate from the shares above), so the CPU chain is the next limit here.
The cheapest win for such PCs is fewer bytes over PCIe a frame (msync / rbrefresh / write-backs), not GPU shader work.

## Executors on a 6-core CPU
The game makes its 6 BaseProcExecutors with masks 0x1..0x20 (one per guest core) and ModuleSystemWorker1-5 on cores
1-5, as on the main PC. The 6 virtual cores are scheduling tokens only (Windows places threads on the 12 logical CPUs).
- During the group waits all 6 executors work 43% (idle) / 41% (move) of the time, mean 3.53 / 3.39 working
  (main PC 41-44%, 3.45): the same two-phase shape.
- Virtual-core waits on the critical path: 0.01-0.05 ms a frame; wake 0.41-0.45 ms a frame (main PC 0.21-0.30),
  executor wake latency after sleeping 8-15 us (main PC 6-6.5 us).
- Walking adds streaming: three ParallelDecompThreads 54-99% busy and OptimizeChangeBanc 67% with 7.7 ms a frame of
  virtual-core waits. On 6 physical cores this is likely the source of the walking 1% lows (4.6-10.8); not proven.
So the TICK-039/042 picture holds: the main thread waits for job code, not for scheduling; the job code is ~2x slower here.
