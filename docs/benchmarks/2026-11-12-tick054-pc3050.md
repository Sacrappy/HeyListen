# TICK-054's defaults on PC 3050 (2026-11-12)

Question: do the new defaults (`HOS_NVN_HOLD=2`, parallel-replay rounds / `SELF=2` / balance / point 32 / ParLock spin 4000,
wide pool table, gone ring, `RX_VK_PARALLEL` by thread count) help or hurt on the 6-core PC? Only before/after on this
machine counts (setup: `2026-11-10-pc3050-baseline.md`).

## Setup
- PC 3050: i5-10400F (6 cores / 12 threads, so 4 recorders by the thread count), RTX 3050, PCIe Gen 3 x4. Runs over SSH (session 0).
- Build: main 32dc46f, exe + dll built in full there (`C:\OOT\scripts\b56.bat`: TICK-055's no-PGO recipe, lift cached from
  `w55base`; object keys: game-code headers 0b8a4589c4, flags 4e8397c788, hot flags 29ed290a78, **lifted code e8dc207cb2**).
  Kept in `C:\OOT\builds\main32d` (exe md5 2979897a, dll bbf74311). The old game build (t53f, PGO exe 223765ae, dll 5a7f4494)
  is backed up in `C:\OOT\builds\pre056`. Note the exe is no-PGO (as TICK-055's): both variants use it, so the A/B is clean,
  but absolute fps are not comparable with the earlier PGO runs of 2026-11-10/11.
- One binary, variants by environment (`C:\OOT\scripts\ab56.py`, `absum53.py`; 110 s runs, 66 s cut, `--fps-limit 360`,
  frame generation off, frame trace on in both; odd rounds base first, even rounds new first):
  - **base**: `HOS_NVN_HOLD=0 RX_VK_PARALLEL_ROUNDS=0 RX_VK_PARALLEL_SELF=0 RX_VK_PARALLEL_BALANCE=0 RX_VK_PARALLEL_POINT=0
    RX_VK_PARLOCK_SPIN=0 RX_VK_TL_POOLS_WIDE=0 RX_VK_GONE_RING=0 RX_VK_PARALLEL=4` (the behaviour before TICK-054).
  - **new**: no environment.

new minus base: castle-move +0.4 fps (new above base in 2 of 3 rounds by pairing, equal in the other; inside the spread),
kokiri-idle +0.9 fps (new above base in rounds 2 and 3, 0.3 under in round 1), 1% low +4.9 (all three new runs 23.5-24.7; base 16.4-24.7), p99 equal. GPU utilisation 62-63% -> 63-64%
(castle-move), 67% -> 69% (kokiri-idle): the machine stays GPU/PCIe bound (see the baseline), so the CPU-side gain of 1.9 to
3.8 fps on the main PC mostly cannot show; the verdict is "does not lose", with a small gain.
**New did not lose: no bisect, no thread-count rule, no engine change.**

## Checks
- Log of every run: base runs show no `submits held` line, 4 recording threads, no rounds, ParLock spin 0, ring off, wide off,
  a point every 64; new runs show `submits held (HOS_NVN_HOLD=2)`, 4 recording threads in one round, `SELF=2`, spin 4000,
  ring on, wide table on, a point every 32 draws (12 of 12 runs, plus the speed run).
- `HOS_SPEED_LOG` (one extra new run, castle-move, `v56-new-speed`): ratio median 59.92 over the whole run, 59.97 over the last
  40 s; 3 of those 40 seconds under 59 (min 58.09). About 60, as intended.
- Saves: `C:\OOT\game\user\save` hash-equal to `C:\OOT\user-save-backup` after every run (checked by pcbench before and after
  each) and once more at the end. No HeyListen process left (tasklist).
- Game folder: main 32dc46f build (exe + dll) in `C:\OOT\game`.

## Not verified
- Frame generation on; a scene change by walking; a PGO build of main on this PC (the exe here is no-PGO).
- Interactive desktop (runs are in session 0).
- 3 rounds a scene is a screen (the PC's spread is 4-5%): the +0.4 / +0.9 fps are not significant on their own; the claim is
  only that none of the switches costs fps or lows here.
