## 1. Where the frame goes (base: main af1cc93, castle-move)

Unprofiled, from the frame trace (`RX_VK_FRAME_TRACE`), nvidia-smi / dmon and a job trace (`HOS_JOBTRACE` 90-93 s,
`tools/bench/chainb.py`, `frameline.py`); run `t60-tr0` (28.3 fps) and the screen's base runs (28.1):

| | ms a frame |
|---|---:|
| frame (trace on) | 35.3 (p50 34.1, p99 57) |
| GPU: recordings (`gpu_ms`, timestamps, not serialised) | 19.7 |
| GPU: upload command buffers (`gpu_up_ms`) | 2.8 |
| GPU idle between recordings (`gpu_gap_ms`) | **12.8** (p50 11.9, p90 18.6; the log: one long gap a frame, 10.6-17.5 ms) |
| nvidia-smi utilisation / dmon PCIe rx | 60% / 544 MB/s (of 3.9 GB/s) |
| the late-page wait (`late_wait_ms`, once a frame, ~100 pages in the Market) | 7.7 |
| the GPU busy with no gap before that wait ends (log `GPU tail`) | 13.6-15.6 |

The frame's serial loop (chainb, 37.6 ms with the job trace): the main thread's draw code to its held submits 0.9 ms -> **the
held flush 11.5 ms** (the capture made 3.1, its memory work 8.1 = the late-page wait on the held submits' host thread, the
Presentation Thread waiting behind it for the replay's lock) -> **the Presentation Thread's submits 23.1 ms** (capture 1.05,
memory work 0.5, dry pass 2.15, **the mirror pre-sync 5.8**, its own segment 5.7, waits for segments 1.6, the small command
buffers) -> the present 2.2.

**Why the GPU idles a third of the frame.** Not PCIe (rx 0.54 GB/s of 3.9) and not the uploads (2.8 ms of GPU work, counted as
busy). Each frame the queue empties once: the held flush waits ~8 ms for the previous frame's last write-back (the GPU busy then,
on that frame's ~14 ms tail), and the CPU only records the new frame after it: the replay's lock is held through the wait, the
Presentation Thread's first big command buffer needs its dry pass and the 5.8 ms mirror pre-sync before anything of it goes to the
GPU. So the GPU waits ~10-12 ms for the CPU's recording of each frame's first work: the frame is CPU wait + CPU recording, not
max(CPU, GPU). The mirror pre-sync is that slow here (0.8 ms on the main PC) because of TICK-048's chunk diff, on by default on
this x4 link: `RX_VK_PRESYNC_STATS` gives 105k pages looked at, 9.3k dirty, 5.2 MB copied, 5.6 ms (page loops 5.5);
with `RX_VK_MSYNC_DIFF=0` 1.5 ms but 34.6 MB copied: ~4 ms of the 5.6 is hashing 37 MB of capture buffers that the capture's
streaming stores left in DRAM.

**The GPU's own time at 1440p** (`RX_VK_PASS_TIMING=1`, base60, run `t60-pt` 27.3 fps: serialised, a timestamp around every span,
so read the shares): 26.0 ms a frame = recordings 21.0 (the game's passes 13.4, its dispatches 4.6, barriers 1.2, write-backs
0.85) + uploads 5.0 (readback refresh 2.0 / 5.5 MB, mirror syncs 1.5 / 4.2 MB, mmake 0.5, ASTC 0.5). The top spans: rbrefresh
scatter 2.0, msync scatter 1.5, pass `1a7482c0ec9991ea` (2560x1440, one draw) 1.08, wb copies 0.85, the upscaler network dispatch
`9dc98871eb7fc101` 0.52, the game's barriers 0.49 (148), pass `d8180bd8c6ecc77b` 0.48, dispatches `ee7764a6b1ef459c` 0.38 and
`27ee9883e2a20323` 0.35, pass `d8e59341cf4f629c` 0.37. In the late wait's tail (18.2 ms a wait, profiled): passes 10.9,
dispatches 2.8, msync 0.9, rbrefresh 0.7, wb 0.5, barriers 0.5. As TICK-057 found: the GPU's own time is the game's full-screen
passes and compute at 1440p; the engine's part is small unprofiled (no new GPU cut tried here: TICK-057 tried them all).

## 2. What was built (all behind switches; branch commits 559d7de..)

**`RX_VK_LATE_DEFER`** (vk_memory.cpp `take_capture`, vk_replay.cpp): the late-page wait moved from the capture's take to the
queue. A take whose late value the queue already has (a signal of it or of a later value was sent, so the GPU reaches it with
nothing more submitted) does not wait: its late slots are noted (a `LateFix`) and the replay goes on recording. Until the fix is
applied every recording is held back (the batched path of RX_VK_BATCH, used for this even where batching is off), and every
submit or flush applies pending fixes first: the same copies the take made after its wait (the late pages from guest memory
into their slots of the capture buffer), at the same moment (the value's end, by a fix thread that then sends the held
recordings). A thread that has to send something waits for the value outside the queue's lock; a fence poll neither waits nor
flushes (in the first try a poll of the main thread's waited 7.5 ms under the lock and held the Presentation Thread). CPU readers of
a pending late slot: a replay read as submitted waits for the value and reads guest memory (as the take's copy would give it); the
mirror sync's chunk diff copies the page whole and keeps no hash of it. Not deferred (waits as before): RX_VK_LATE_MERGE on, a late
page in a live texture's storage, a value not sent yet, 4 fixes pending. Trace marks 38/39 (the fix thread), log lines
`late pages deferred`, `late fixes`, the trace column `late_fix_ms`. Why the picture cannot change: the GPU reads the same bytes
(each submission that may read the capture buffer goes to the queue only after the fix), and the CPU's own readers wait for them.

**`RX_VK_CAPTURE_HASH`** (vk_memory.cpp `copy_part`, msync_diff.h `copy_hash_page`): the capture's copy makes TICK-048's chunk
hashes of each page in the same pass (each 32-byte load stored and hashed from one register: the hashes are those of the bytes the
slot received, even with the game writing the page meanwhile); the mirror sync takes them instead of reading the capture buffer
back from DRAM to hash it. Same hashes (tests/test_msync_diff.cpp: bit-exact against memcpy + page_hash, with and without AVX2,
aligned and not), same chunks copied, same mirror. A slot copied again after the copy (a late page after the take's wait or at
its deferred fix) loses its hashes and is hashed by the sync as before. Only with the diff on and an AVX2 build.

**`RX_VK_MSYNC_FAST`** (TICK-056's, unchanged): the mirror sync's walk straight to the next dirty page.

## 3. Traces (one run each, castle-move, job trace 90-93 s)

| run | build / env | fps | frame ms (trace) | gpu_ms | gpu_up_ms | gap ms | late wait | GPU % | pre-sync ms |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|
| t60-tr0 | base60 | 28.27 | 35.3 | 19.7 | 2.8 | 12.8 | 7.7 | 60.0 | 5.8 |
| t60-tr3 | t60c LATE_DEFER | 30.12 | 33.2 | 19.6 | 2.8 | 10.7 | 0 | 64.5 | 5.7 |
| t60-tr4 | t60d LATE_DEFER + CAPTURE_HASH + MSYNC_FAST | 33.12 | 30.1 | 19.5 | 2.75 | 7.8 | 0 | 71.3 | 1.6 |

With the deferral the held flush falls from 11.5 to 4.6-4.8 ms (its memory work 8.1 -> 1.3 ms), and the frame becomes the CPU's
recording chain; the pre-sync's hashing (4 ms of 5.6) is then on it, which the capture's hashes take off: `RX_VK_PRESYNC_STATS`
5.6 ms (looked at 105k pages) -> 4.7 (MSYNC_FAST: 8.7k) -> 1.6 (with CAPTURE_HASH: the syncs took 1386 slot hashes a submit and
hashed 17 again). The capture's copy did not get slower (0.45 ms a submit's copy in both: memory-bound, the hash is ALU).
The bytes over PCIe are unchanged (scatter 6.0-6.1 MB a frame; dmon rx 544 -> 646 MB/s, the same bytes at more frames).
