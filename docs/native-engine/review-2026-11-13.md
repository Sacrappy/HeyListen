# Review of the hybrid engine's first day (2026-11-13)

One reading of everything merged under `engine/` between `397eb4a5` and main at `99e28696` (86 files, 15,000 lines), for
the defects the three validation scenes cannot show: off switches, threads, memory safety, portability, the players'
build, tests, house rules. Ranks: **A** wrong behaviour or a failure a player could meet; **B** needs a specific
condition (a platform, a race, another lift or build of the game); **C** hygiene. Each finding: where, what, a scenario,
the fix. Fixed findings name their commit on `stream/s9-review`; the others say who should take them.

## A

### A1. The Windows release does not ship `engine/native`: every player's build fails (fixed, `4a6a1097`)

`engine/scripts/release_parts.py` `package()` copied the tracked files of `assets gpu host nx2 scripts third_party` into
the builder's `tools/`; not `native`. `nx2/build.py` reads `native/include/hl/c` unconditionally for the host objects'
dependency key, so a released builder stops at its first compile step. Fix: `native` added to the list;
`tests/test_release_ships_native.py` checks it (and the AppImage's list, B1).

### A2. A builder update that changes the gate list leaves stale gates in an existing lift (fixed, `27eb1197`)

The entry gates are put in by `hl_gates.apply`, which ran only inside the lift (`lift.py` -> `chunks.edit_c` ->
`oot_patches.apply`). `make_game.py` skips the lift when its key is unchanged, and the key covers `nx2/`, the a64-kit
and the names of the HLE functions, not the `HL_GATE` lines in `host/hl_*.c`. On a PC that lifted before:
- an update that adds a gate (or the same address with a new hash) leaves the lifted code without it: the module logs
  "on" and nothing is answered;
- an update that drops a gate (the module dropped, the address moved to `HL_ANSWER`) leaves a gate line calling
  `hl_gate_<addr>` and reading `hl_gate_on_<addr>`, which no host file defines any more: the link fails on two undefined
  symbols at every build until the player forces a new lift.
Fix: `make_game.py` applies the gates after the lift step whether the lift ran or was skipped; when that changes the
lifted files it writes the lift key again (the files were what the key vouched for just before). Verified by the
make_game and lift tests of the suite; not by a player's update (no release made here).

## B

### B1. Linux: the game no longer builds (fixed in part: `4a6a1097`, `38ee1bed`)

Four breaks, any one of which stops a Linux build:
1. `host/hl_stream.c` (`page_view`, `HL_STREAM_PAGES`) calls `ReadProcessMemory`, which the POSIX shim did not provide;
   the file has no `_WIN32` guard. **Fixed**: the shim answers it with `process_vm_readv` on this process, which fails
   with EFAULT on an unmapped page as Windows' copy fails.
2. The AppImage (`scripts/linux/appimage.sh`) copied neither `native/` nor `third_party/zstd/lib`, both compiled into the
   game now. **Fixed** (and checked by `tests/test_release_ships_native.py`).
3. The AppImage's sysroot removes the C++ headers (`rm -rf $S/usr/include/c++`) and carries no `libstdc++`: the native
   tree (C++20 with `<atomic>`, `<vector>`, `<thread>`...) cannot compile against it, and `build.py`'s Linux link adds a
   `-lstdc++` that is not there. The Vulkan back end, the other C++ of the game, is built in CI and shipped prebuilt with
   its runtime linked in (`-static-libstdc++`), which is why this never came up. **Left** (a decision: ship libstdc++'s
   headers and static library in the sysroot and link it statically, or build the native tree with the bundled LLVM's
   libc++): for whoever owns the Linux builder.
4. Even on a source build with a system compiler, the dynamic `-lstdc++` makes the executable depend on the build
   machine's `libstdc++.so.6`, where the back end carries its own. **Left**, with 3.
Not verified on Linux: there is no Linux compiler on these PCs (WSL has none installed).

### B2. A gate missing from a lift leaves its module half on; the stage trio is not independent (left: jobs)

`hl_gates.py` puts each gate in only when that function's lifted text hashes as recorded. The text includes what
lift-time switches make of it (the FPX block form, among others) and the hot chunk a function is in follows the play
profile shipped with a release. A lift whose text differs for one function leaves that gate out with a line in the
build log; the module still sets `hl_gate_on_<addr>` and logs "on", and nothing tells it the gate is absent. For most
bricks that is the brick silently off. For `HL_STAGES` it is worse: the registration `0x806b0260`, the stage wait
`0x806afc40` and the last stage `0x83acfb90` share the registered mask and count and are switched on together
(`hl_jobs.c`), so a lift with one of the three gated and another not runs a native registration against a translated
wait (or the reverse) for every stage. Scenario: a release ships a new play profile or lift default that changes one of
the three functions' text. Fix (a decision for the jobs stream and `hl_gates.py`): let the build tell the modules which
gates are in (for example `hl_gates.py` writing the list of gated addresses into a generated file the host links), and
have `hl_jobs.c` turn the trio on only when all three are in; until then, a check in the release process that every
`HL_GATE` hash matches the release's own lift.

### B3. `HL_MATH`: a call can take the native path after `start()` turned its unit off (left: math)

`hl_math.c` `run()` and `run_body()` test `native_on`/`check_on` only when they are the ones that call `start()`. A
thread that read the gate's switch (set to 1 by the constructor) before another thread's `start()` cleared it, and
enters `run()` after `start()` finished, goes on to the native kernel (or, in check mode, to `u->translated`, which is
NULL when the lifted table has no such function). Conditions: the first calls of a unit on two threads at once, and a
unit that `start()` turns off (another build of the game whose function text happens to hash the same, or no
translated function). Fix: test `u->native_on || u->check_on` on every call, not only after `start()`.

### B4. `nn_os_sync.c`: the mutex-number counter wraps once the table is full (fixed, `b67fe062`)

With the 2^20 numbers given out, every lookup of a mutex without one still incremented `mx_next`, a 32-bit `long` on
Windows; at the game's lock rate it wraps negative within the hour, passes the test against the cap and writes
`mx_objs` below its start. Reaching 2^20 numbered host objects is not expected (objects are reused), so this needs a
game or mod that makes that many mutexes. Fix: the counter is read first and left alone at the cap.

### B5. The native tree's tests were not built as the game builds it (fixed, `fa152f95`)

`tests/test_native_engine.py` compiled `engine/native` with `-mavx2 -mfma` and the compiler's default contraction
(clang: within a statement; GCC: anywhere), while the game compiles it with this PC's `-march` and `-ffp-contract=off`
(`nx2/build.py` `CPU`). A math test could pass on fused multiply-adds the game never executes (the bit-exact claims of
`hl::math` rest on those tests and on the in-game check), and the test programs could not run on a CPU without AVX2.
Fix: the game's flags (`host_cpu.host_march()`, `RX_MARCH` honoured, `-ffp-contract=off`). Passes with clang++ at
x86-64-v3 and at the x86-64 baseline. Nothing in the tree uses AVX2 or FMA intrinsics (the only intrinsic is
`_mm_pause`), and the FMA of `hl/math/Exact.h` is computed through binary64, so the game's build for CPUs without AVX2
is not affected.

### B6. The flaky `tests/test_readback_ticket.py` (fixed, `bcd16bd9`)

The test's stress part starts after two sections made by the main thread that registered nothing. A poll that ran
before the first replay section (the replay threads start late under a loaded parallel suite) took the last of those
sections as its ticket, rightly did not wait, and found the registration counter behind it (`FAIL:114`). Reproduced
once in six parallel runs; forced with the replay threads' start delayed 100 ms it fails every time without the fix and
passes with it. A fault of the test, not of the ticket.

### B7. A 1 MB commit on first touch resets the protection of pages already committed in that megabyte (left: memory)

`mkw_glue.c` `commit_on_touch` commits the whole megabyte around a touched reserved page (`VirtualAlloc(MEM_COMMIT,
PAGE_READWRITE)`), which also sets read-write on pages of that megabyte that were committed with another protection.
Today that is only `HOS_POOL_TRAP`'s NOACCESS pages (a measurement, off by default), whose touches are then missed, and
the trap does not know. It becomes a correctness matter for any later use of page protection in the heap or the
regions (a guard, a read-only page). Fix: commit only the reserved runs of the megabyte (a `VirtualQuery` walk, as
`vk_memory.cpp` `import_pool` does for the same reason), or call `hos_pool_trap_release` on the megabyte first.

## C

1. `host/hl_stream.c`: `hl_stream_chunk_on` returns `check_on`, which `hl_stream_on` sets; the two answers are asked at
   each address's first lookup, so the check's chunk collection depends on the decode function being looked up before
   the chunk function (it is, in practice: a chunk is handed over only by a decode). Reading the switches in a
   constructor, as `hl_math.c` does, removes the order.
2. `host/hl_stream.c` records every decode in the provenance table (a map insert, a string, a lock and an 8 KB
   fingerprint a file, on by default) that nothing reads outside the `HL_STREAM_PAGES` measurement, and
   `hl_stream_forget` is never called, so entries outlive the memory they describe. The module's own document calls it
   "not used yet"; until it is, it could be recorded only with `HL_STREAM_PAGES`.
3. `hl::app::MainLoop` is built into the game and used only by its test (the native main loop is not on any path).
4. `HL_JOBS=1` (the default) starts the job system's six pool threads (64 MB of stack reserved each) that never run a
   job in that mode (only guest jobs are submitted, and `guest_on_workers` is off).
5. `HL_JOBS=2` (pool mode) is documented as "not for use yet" since its stall: a switch with no supported use.
6. `hl::mem::ColdPages::look` and `taken_out` read and write a unit's word in two steps while `forget` (a pool made, on a
   game thread) exchanges it: a pool made during a pass can have its reset overwritten. The words are advice (data is
   never at stake: a page taken out of the working set keeps its bytes); the out-page counter can drift.
7. `hl_mem.c`: imports the back end makes before `hl_mem_init` are not marked (the notification is dropped while
   `cold_on` is 0). Harmless (a trim of locked pages does nothing), but the "never taken out" list is incomplete.
8. Comments dated 2026-11-14 in `gpu/vk/vk_texture.cpp`, `vk_memory.cpp` and `host/hl_math.c` (the review date is
   2026-11-13: the dates are a day ahead).
9. `host/hl_math.c` check mode copies a unit's inputs for the mismatch log from guest addresses computed from guest
   values (`sphere_inputs`) without `hos_guest_range`; a null pointer there faults in check mode only.
10. `host/nn_fs.c` committed the guest buffer of every file read and write (`hos_commit`: a `VirtualAlloc` over the
   buffer rounded out to 64 KB) whatever `HOS_LAZY_COMMIT` said; with it at 0 the buffer is committed already, so the
   call was a system call a read for nothing, and on Linux (lazy commit off by default) the shim's commit changes the
   pages' protection each time. **Fixed** (`HOS_LAZY_COMMIT=0` means as before again). (Recent runs' logs show no failed
   commit with it on.)

Checked and found right: `HL_ANSWER`'s once-per-address state machine and the build check before any `on()`; the
runtime lookup's cache of a replaced function; every module's `0` switch (no thread started, no gate left on: `hl_gfx.c`
turns its gates off at their first call; `hl_math.c` sets them from the switch in a constructor); on another build of the
game every brick is off (gates whose hash differs are absent, and the `HL_ANSWER` ones never ask `on()`); the job
system's single mutex and its two condition variables (every wait is a loop on the state, every state change that can
make work runnable notifies the sleepers it can concern, lanes given back included); the no-access pools' decommit
(checked and decommitted under the write lock the back end's writes take, never in an imported range); the mutex
numbers against reuse of host objects; the readback ticket's wake-up; `snprintf` accumulations in the report functions
(all bounded before they could pass their buffer); the 64 KB / 1 MB / 4 KB rounding in `hl_mem.c` and `hos_memsplit.c`;
`nn_fs.c` committing a guest buffer before the kernel reads or writes it (with lazy commit on); the `-lstdc++`-free Windows link (the game's
C++ runtime comes with `-lc++` there). No translated code is quoted in the documents, the comments or the tests read
(searched for lifted-C and instruction patterns).
