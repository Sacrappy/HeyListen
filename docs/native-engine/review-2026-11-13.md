## A

### A1. The Windows release does not ship `engine/native`: every player's build fails

`engine/scripts/release_parts.py` `package()` copies the tracked files of `assets gpu host nx2 scripts third_party`
into the builder's `tools/`. `native` is not in the list, so a released builder has no `tools/native`, and
`nx2/build.py` reads `native/include/hl/c` unconditionally to make the host objects' dependency key: the build stops on
a missing folder before compiling anything. Fix: `native` added to the list.

### A2. A builder update that changes the gate list without a new lift leaves the lifted code's gates stale

The gates are put in by `hl_gates.apply`, which runs only inside the lift (`lift.py` -> `chunks.edit_c` ->
`oot_patches.apply`). `make_game.py` skips the lift when its key is unchanged, and the key covers `nx2/`, the a64-kit
and the names of the HLE functions, not the `HL_GATE` lines in `host/hl_*.c`. So on a player's PC that already lifted:
- a release that adds a gate (or the same address with a new hash) leaves the lifted code without it: the module's
  switch logs "on" and nothing is answered;
- a release that removes a gate (the module dropped, or the address moved to `HL_ANSWER`) leaves a gate line in the
  lifted code calling `hl_gate_<addr>` and reading `hl_gate_on_<addr>`, which no host file defines any more: the link
  fails with two undefined symbols, at every build, until the player forces a new lift.
Fix: `make_game.py` applies the gates after the lift step whether the lift ran or was skipped, and when that changed
lifted files it writes the lift key again (the files were as the key vouched for just before).

## B

### B1. Linux: the game no longer builds

Four independent breaks, any one of which stops a Linux build:
1. `host/hl_stream.c` (`page_view`, HL_STREAM_PAGES) calls `ReadProcessMemory`, which the POSIX shim
   (`host/posix/windows.h`, `win32_posix.c`) does not provide: undefined at the link (the file is compiled on Linux:
   it has no `_WIN32` guard).
2. The AppImage (`scripts/linux/appimage.sh`) copies `nx2 host gpu/... third_party/{opus,kenney_input,zbic,a64-kit}`
   into the builder, not `native/` and not `third_party/zstd/lib`, both of which `nx2/build.py` now compiles into the
   game.
3. The AppImage's sysroot removes the C++ headers (`rm -rf $S/usr/include/c++`) and carries no `libstdc++`: the native
   tree (C++20, `<atomic>`, `<vector>`, `<thread>`...) cannot compile against it, and `build.py`'s Linux link adds a
   dynamic `-lstdc++` that is not there either. The Vulkan back end, the other C++ in the game, is built once in CI and
   shipped prebuilt with its C++ runtime linked in (`-static-libstdc++`), which is why this never came up.
4. Even on a source build with a system compiler, the dynamic `-lstdc++` makes the executable depend on the build
   system's `libstdc++.so.6`, where the back end was made to carry its own.
Fixed here: 1 (the shim answers `ReadProcessMemory` with `process_vm_readv`, which fails on an unmapped page instead of
faulting) and 2 (the AppImage copies `native/` and zstd's `lib/`). Left (needs a decision on the C++ runtime for
players' Linux builds: ship libstdc++'s headers and static library in the sysroot, or build the native tree with the
bundled LLVM's libc++ and link it statically): 3 and 4. Not verified on Linux: no Linux machine here.
