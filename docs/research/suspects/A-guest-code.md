# Suspects A: the game's own code on chain A (guest functions)

Read-only analysis, 2026-11-11. No game run, no build. Guest functions are named by address only.

## Data used and how to read the numbers

- **P** = TICK-058 `inst-castle-move` (`critpath.txt`, `all.txt`, map `bin/inst/HeyListen.map`): the walked critical path, 188 frames, 15.85 ms/frame. Only 6.8 s of samples (715 per thread), so single functions carry +-30% noise.
- **B** = TICK-052 run `B` castle-move (main PC, 70.6 fps, 14.16 ms/frame, 31.9 s, 7,472 samples per thread, map `bin/B`). Used for per-function CPU. Conversion: CPU ms/frame = sample count x 14.16/7472 = x 0.00189. This is **thread CPU summed over threads, not wall time on the chain**. B's lift is the same as the current one (same function addresses).
- I aggregated both with my own scripts (scratchpad, using `engine/scripts/prof.py` and the maps). Sizes: x86 bytes from the map, guest instruction counts from `sa/gen/functions.txt`.
- "measured" = from those files. "estimated" = my arithmetic on top (assumed speed-ups are stated).
- Total guest-leaf CPU in B: 31.9 ms/frame (plus 7.8 of host leaves). The profile is flat; no function exceeds 4% of its group. Gains therefore come from families of kernels and from runtime calls, not from one hot spot.

## Findings that shape the ranking

1. **The NavMesh crowd thread is on the critical path and nobody has looked at its code.** `NavMeshCAStepDepWorker1` is the 2nd biggest "work" entry on the walked path (1.176 ms/frame, `critpath.txt`), runs 26% of its time (3.7 ms/frame CPU, B), and 62% of its running samples are in four lifted FP kernels (f_820e2520 36%, f_81e69500 17%, f_820e1d60 8%, f_820e3140 4%) plus the nn::os helpers f_80043e50/f_800453f0 (13%).
2. **Lifted FP kernels are 150-270 x86 bytes per guest instruction** (whole image: 24.7 B/insn; 436 MB / 17.6 M insns). f_81b8c000: 17.4k guest insns -> 3.97 MB x86. f_820e2520: 455 insns -> 94 KB. f_8173a830: 207 insns -> 48 KB. Front-end pressure has never been measured (TICK-055 classified instructions only).
3. **22.9% of guest-leaf samples (8.1 ms/frame CPU in B; 22.5% in P) are in -O1 non-PGO chunks.** TICK-040 already extended the hot set (93-96% coverage) with no fps gain, so I do not propose it again. It does mean f_820e1d60, f_817472e0, f_801d7ac0 run without PGO today.
4. **Library-like guest code is not where the time is.** memcpy/memmove/memset/memcmp/strlen/strcmp are already host hooks (`host/nn_libc.c`). All guest functions at 0x85xxxxxx (libm/thunks) together are 0.9 ms/frame CPU in B (largest f_85751760 0.14, f_8575cdc0 0.13, f_8572f300 0.10). The ucrtbase memcpy seen in samples is the engine's NVN recording copy, not guest libc.
5. The one libm call that is everywhere is `sqrtf` (f_85754d70, 2 guest insns): 70 call sites in f_801d99a0. It sits in a cold chunk (code_053.c) and goes through a full Ctx call plus the out-of-line `a64_fpx_sqrt32_sqrt32`.

## Short notes on the top five

**A1, NavMesh crowd step.** `critpath.txt` lists `NavMeshCAStepDepWorker1` at 1.176 ms/frame of work on the walked path, behind only main (1.30) and EX0 (1.08), plus 0.33 ms of virtual-core wait and 0.08 of queue hand-off. The thread's own profile is concentrated: in both datasets f_820e2520 is 36% of its running samples (a 455-instruction kernel with ~200 FPX helper uses, one callee, 16 stores) and f_81e69500 17%. f_820e1d60 sits in a cold -O1 chunk. These are the "self-contained FP kernels" that hotmap.md and TICK-039 priced at ~0.1 ms each, but that was priced for the executors (parallel). Here they sit on a single chain thread, so every ms saved is a ms off the chain. The framework exists (`engine/nx2/native_replace.py` gate + `host/hos_native.c` diff mode); only the strcmp replacement uses it today. Exactness plan: native SSE kernel guarded by the same gate (`RECOMP_FPX_OPEN`) and the same keep tests; on any failed lane or closed gate, fall through to the lifted body. First step (a day): bench an f_820e2520-style kernel in `lifter_mb` to see the ratio before writing the SIMD version.

**A2/A3, FP kernel families.** The ten kernels in A2 (all <= 270 insns, no real calls) are 2.8 ms/frame of CPU in B. The 4-executor last stage and the Link-dependent jobs (f_83af59c0 -> f_800a8400/f_80ba37a0) are on the chain; the rest are in the parallel phase. Hand-writing ten SIMD kernels is possible but each needs its own diff run; A3 solves it once in the lifter: evaluate a region optimistically, test the accumulated masks once. It reuses the keep tests already validated in `fpx_xmm_test.c`. TICK-055's per-op XMM pinning did not pay because the keep tests need result bits per op; a block form keeps intermediates in XMM and tests them in bulk. Expect a larger win in the kernels than in the whole game; it needs a PGO profile recorded on that lift (TICK-045).

**A4, the mutex storm.** The module worker's serial job (f_80083580, 2.7 ms/frame) calls f_80660320 for about 8,000 locks a frame; each reaches `obj_lookup` and misses (TICK-042: a larger cache did not help, the objects are cold, once a frame). P shows f_80364080 at 2.9% of the path's samples. The untested idea in perf-audit (TICK-037 item 3, TICK-042 item 5) is to keep the lock state next to the guest object instead of looking the object up in a 220k-entry table: one cache line (the guest's own, close to data the game just touched) instead of three. It needs proof that the game never reads those MutexType words; a static scan of loads from the lock object in f_80364080 and its callers answers that.

**A5, NVN recording in guest threads.** These engine functions run on the module workers and the main thread, inside chain A. In B the module workers spend 0.63 ms/frame (thread time) under CallCommands with an ntdll leaf and 0.44 under AddControlMemory, which looks like waiting on `copy_lock` (shared by the recorders, taken exclusively by `release_copies`/`free_dead_copies`) rather than copying. EndRecording's `flatten` memcpy adds 0.13. Check by tracing lock wait time; if confirmed, shard `copy_lock` by control-memory block (the buckets already are) or defer `release_copies` to the replay thread. This overlaps the graphics agents' area; flagged because the cost lands on chain A.

**A6, resource decompression.** Two integer functions (f_801102e0, 345 insns; f_80110860, 970) are 2.77 ms/frame of CPU in B, more than any guest function except the NavMesh kernel and Link's calc. hotmap.md guessed it is off the frame; the P path walker shows `ARes_Loading_1/0/3` doing 0.77 ms/frame of path work, so at least in some frames the chain waits for loads (a module poll or message to a loader). That needs one trace check before code is written. The replacement is the lowest-risk kind: integer only, byte-exact output, diff mode compares the destination memory, and a native AVX2/BMI decode of an LZ loop is typically 3-5x faster than the lifted form (each guest store carries page-mark work and a poll).

## Not proposed (already tried or measured as not paying)

Host sync primitives, priorities, spin (TICK-039/054/058); `A64_FPX_XMM`, `A64_LR_SCALAR` (TICK-055); MSYNC_FAST/SEG_EARLY/LATE_MERGE; lock-free fence poll; larger hot set / PGO profile (TICK-040: 93% coverage, no gain); larger object cache (TICK-042); `HOS_CORES=8`, pinning (TICK-039). Not worth it from my data: libm/thunk functions at 0x85xxxxxx (0.9 ms/frame CPU in total, <= 0.1 on the chain), guest memcpy-like loops (hooked already), `a64_icall_site` (it is in ~50% of path stacks only as a frame; its lookup is 0.15 ms/frame CPU), executor idle spin (`spin_until_set`, 2 ms/frame CPU but off the path).

## Suggested order of work

1. Measure first (half a day, no code): `lifter_mb` ratio for an f_820e2520-style kernel; trace whether the chain waits for `ARes_Loading_*`; wait time under `copy_lock`; AMD IBS fetch counters on one executor (A11, A9).
2. Cheapest wins: A10 (thread core mask), A7 (64-bit sticky rescue, per-lane `_lanes`), A8 (f_80029240).
3. A1 as the first real native kernel; if its ratio is >= 2.5x, commit to A3 (lift-time) instead of hand-writing A2.
4. A4 with the static proof; A5 after the lock trace.
