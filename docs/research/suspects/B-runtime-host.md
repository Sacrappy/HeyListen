# Suspects, area B: the runtime and host layer under the guest code (chain A)

Read-only audit. Nothing was built or run. Evidence: `engine/docs/perf-audit.md` (TICK-039, 054, 058), the TICK-058 samples and
traces in `E:\OOT\HeyListen-wt\TICK-058\build\tick058\samp\inst-castle-move\` (`all.txt`, `jobtrace.txt`, `critpath.txt`; symbols from
`bin\inst\HeyListen.map`), and the code. "measured" = from those files; "estimated" = my arithmetic, to be confirmed by the check in the table.
Sample shares below are shares of the non-blocked samples of the named threads, recomputed from `all.txt` (castle-move, trace window on).

Bottom line: the host sync layer itself is already tight (TICK-039/058: wake 0.2-0.3 ms, primitives 0.3-0.5 ms). What is left in this area
is (1) work the guest makes the host do for nothing (NavMeshCAStepDepWorker1's signals and priority queries), (2) the virtual-core model
serialising threads that share vcore 1, (3) a few shared locks and linear scans, and (4) syscall-polling loops. The realistic items sum to
about 0.5-1.0 ms on chain A; no single item is above ~0.4 ms.

## Notes on the top five

**B1, the unobserved condition-variable signals.** The TICK-039 note is confirmed: 1.71 M cv signals in the 3 s window, 95% of them from NavMeshCAStepDepWorker1, none of its cvs ever waited on (CV_WAIT_B has 2 records in the file). A signal with no waiter has no guest-visible effect: `gen++` is only read by a waiter that entered earlier, and `cv_reserve` already does nothing when `cv_waiting <= cv_owed`. So SignalConditionVariable can read `cv->cv_waiting` (made atomic; it is incremented in `cv_enter` under the lock, before the guest mutex is released in WaitConditionVariable) and return before the lock, `gen++` and the wake. Ordering: a signaller holding the guest mutex sees the waiter, because `mutex_release_all` (seq_cst exchange) comes after `cv_enter`. A mutex-less signaller racing the few nanoseconds between the waiter's `gen` read and `cv_enter` loses the signal, the same window a real wait has between predicate check and the kernel wait. What is left per signal is obj() plus a load. Keep the checkpoint (it is what lets EX1 kick this thread off vcore 1) and the `HOS_JT` and watch hooks. Gate with an env switch; nothing visual should change.

**B2, thread lookup by guest address.** `hos_thread_of` scans `threads[]` linearly behind a shared SRWLock whose cache line every caller writes. NavMeshCAStepDepWorker1 calls GetThreadPriority about as often as it signals; 7.1% of its active samples are in that HLE. Fix: a per-thread direct-mapped cache `{guest_tt -> HosThread*}` validated by `t->guest_tt == tt` and a global generation bumped in `track()` and `hos_thread_destroy`, or a lock-free open-addressing table. Pure host data structure. Small gain, cheapest and safest item.

**B3, the vcore-1 pile-up.** Measured in `critpath.txt`: NavMeshCAStepDepWorker1 waits 220 us a frame behind EX1 and 111 us behind Resource_Memory, plus a queue hand-off of 163 us mean (0.51 a frame, 82 us on the path), the largest hand-off item of the game's chain. Virtual cores exist because the game keys per-core data (allocators, job queues) by core number without locks. A thread whose code never reads the core number cannot depend on it, so step one is a free measurement: count, per guest thread, GetCurrentCoreNumber and svc 0x10 calls. If NavMesh, Resource_Memory, ParallelDecompThread and ARes_Loading_* never ask, they could take an alias vcore and stop queueing behind the executors. Risk is high: data tied to the core by position, or a core number read the host does not see, would corrupt per-core tables. Ceiling 0.4 ms on the path.

**B4, the poll loop made of syscalls.** `sleep_ns` below 1 ms loops `SwitchToThread()` (a syscall) with a QPC read each time. The module-poll sleeps are ~44 a frame on main and on each module worker, so these six burn ~5 ms of CPU a frame there. TICK-039/058 showed the step length and the wake do not matter, but nobody looked at what the polling does to SMT siblings, which are the executors (16 logical CPUs, ~18 busy host threads). Try `SwitchToThread` once, then a `YieldProcessor` loop against a TSC deadline, behind an env switch. Vcores are released for the sleep, so nothing guest-visible changes. The gain may be zero; it is the only low-risk item aimed at the 15-20% ntdll share.

**B5, file reads on the loader threads.** ARes_Loading_* spend ~60% of their active samples in ReadFile and are on the path for 0.77 ms a frame at the castle. `read_at` issues one overlapped ReadFile per game read and then marks the destination. First step is measurement (reads a frame, size histogram, cold vs cached). Many small reads: a mapped view per RomFS file removes the per-call syscall. Large cached reads: the copy is memory-bound and only an earlier start (prefetch) helps. `OpenFile` also does two `getenv` calls, host_path and the ultrawide redirect on every open; harmless unless opens are frequent.

## Checked, not worth a ticket

- `mutex_lock` / `mutex_take` (CAS on the owner, SRW only for sleepers): minimal already, 0.45% of executors, 0.18% overall. `mutex_give` takes the lock only when `mwait` is set (2,822 contended gives in 3 s).
- Soft-FP helpers: a64_fpx_* ~2.5% of executors; `recomp_fpe_fma64` 0.3%, `recomp_fp_estimate` 0.2%. TICK-044's switches measured inside the noise; no new host-side lever.
- svc dispatch: kernel waits are rare (207 K_WAIT records in 3 s).
- nn_hid, nn_audio: once-a-frame work; AudioFrameworkThread holds a vcore 2.7-4.7 us a frame against EX2-4.
- `hos_self()` / `cur` are `_Thread_local`; `hos_vcore_checkpoint` is 0.05% of samples. Inlining it is noise.
- Event wake latency (p50 6.4 us, 0.2-0.3 ms a frame) and spin length: closed by TICK-039/058.
- ucrtbase (memcpy) under `n_nvnCommandBufferEndRecording` / `inline_recording` is 9% of main's active samples: the NVN recording copy, for the NVN/GPU agent.
- Trace-only cost (`hos_jt_rec` 2.5% in the NavMesh profile) disappears with the trace off; not counted.
